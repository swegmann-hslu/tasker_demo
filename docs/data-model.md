# Conceptual data model

This document describes the information TaskCraft needs for the initial use
cases. It is independent of a particular database or Python persistence
library. Database-specific types and constraints can be decided when
persistence is implemented.

## Task

A task represents a piece of work belonging to one user.

| Attribute | Conceptual type | Required | Description |
| --- | --- | --- | --- |
| `id` | Unique identifier | Yes | Stable identifier generated by the application. |
| `title` | Text | Yes | Short name of the task. It must not be blank. |
| `description` | Text | No | Additional details. An empty description is allowed. |
| `due_date` | Date | Yes | Calendar date by which the task should be completed. It does not include a time of day. |
| `creator_id` | User reference | Yes | User who created and owns the task. This controls who may view or change it. |
| `assignee_id` | User reference | Yes | User expected to complete the task. In the first version this must equal `creator_id`. |
| `is_done` | Boolean | Yes | Completion state. It is `false` when the task is created and becomes `true` when it is marked as done. |

## User reference

The use cases require the application to distinguish users, but registration,
authentication, and profile data are not yet part of the agreed scope. A user
reference therefore represents an application user whose identity is supplied
by a mechanism to be selected later.

## Relationships and rules

 * One user may create and own zero or more tasks.
 * Each task has exactly one creator and exactly one assignee.
 * For the first version, a task's assignee must be its creator.
 * Only the creator may view, complete, or delete the task.
 * A new task is always created with `is_done` set to `false`.
 * Deletion permanently removes the task; archived or soft-deleted states are
   not modeled yet.
 * Priority is deliberately not part of the model.

## Possible later extensions

Team tasks will require explicit decisions about team membership, task
visibility, reassignment permissions, and whether creator and owner remain the
same concept. Those concerns are not included pre-emptively in this first
model.
